# 04 Login and Projects

> Builds on the local foundation of spec 02a: PostgreSQL with RLS, login with Better Auth in the Covibes server, and a web app that only talks to the server API.

## Goal
Users can sign in by email link, create projects and open them. The GitLab login is built in and gets enabled as soon as an OAuth application exists. The database protects every project with RLS, and tests prove it.

## Design decisions
- **Permissions:** `architecture.md`, sections "Auth and permissions" and "Data model". Roles: `owner`, `editor`, `viewer`.
- **Login:** Better Auth on the server under `/api/auth/*`.
  - tables `users`, `sessions`, `accounts` and `verifications`, columns in `snake_case`, UUIDs generated by PostgreSQL
  - Better Auth generates the schema as SQL; it is reviewed and committed as a migration.
  - plugin `magicLink`: the link is valid for 10 minutes and only once. New users are created on their first sign-in.
  - GitLab as a provider, only when `GITLAB_CLIENT_ID` and `GITLAB_CLIENT_SECRET` are set (scope `read_user`, redirect `http://localhost:5173/api/auth/callback/gitlab`)
  - no password login
  - rate limits are on, the origin is checked (`trustedOrigins`)
- **Local email:** a mail interface on the server. Locally, mails land in an in-memory development mailbox, which the web app shows at `/dev/mails`, in development mode only. Real delivery comes with the deployment.
- **Data through the API:** the server reads and writes exclusively through `withUser`, i.e. with the app role and the user id. Creating a project goes through the SQL function `create_project(name)`, which creates project, owner membership and main board in one step.
- **Screens:** login and project list have not been designed yet. They stay plain and only use the tokens and building blocks from spec 03: centered card, panel style. The final design comes with spec 33.
- **No images from GitLab:** the GitLab avatar is stored but not displayed yet; loading it in the browser would send the IP address to GitLab. Initials are shown instead.

## Implementation

### Migrations (`packages/db/migrations/`)
- **`0001_auth.sql`:** Better Auth's tables. `users` additionally gets `locale` (default `de`). RLS is on. Only `covibes_admin` has access; the app role may read `id`, `name`, `image` and `locale` from `users`.
- **`0002_projects.sql`:**
  - enum `project_role` (`viewer`, `editor`, `owner`, ordered by privilege)
  - `projects`: `id` (UUID), `name` (1–120 characters, trimmed), `owner_id`, `language` (default `de`), `settings` (JSONB object, default `{}`), `created_at`, `updated_at`
  - `project_members`: `project_id`, `user_id`, `role`, `can_approve_git` (default `false`), `created_at`, primary key `(project_id, user_id)`
  - `boards`: `id`, `project_id`, `title`, `kind` (`main` or `extra`), `position`, `created_at`. Every project has exactly one `main` board.
  - helper functions in the schema `private`: `is_member(project_id)`, `has_role(project_id, min_role)`, `shares_project_with(user_id)`. All are `security definer`, `stable` and have a fixed `search_path`.
  - `create_project(name)`: creates project, owner membership and the `main` board ("Haupt-Canvas").
  - A trigger prevents a project from losing its last owner.
  - Privileges and RLS:

| Table | Read | Write |
|---|---|---|
| `users` | oneself and members of shared projects (only `id`, `name`, `image`, `locale`) | only Better Auth (admin role) |
| `projects` | members | name, language and settings only the owner; deleting only the owner; creating only via `create_project` |
| `project_members` | members | only the owner. The last owner can neither leave nor be demoted. |
| `boards` | members | owners and editors; nobody can delete the `main` board or create a second one |

### Database tests (`packages/db`)
- A stranger sees neither project nor members nor boards, and only themselves in `users`.
- A viewer cannot change anything.
- An editor cannot change project settings but can create boards.
- Nobody can make themselves owner, change other users or change the column `owner_id`.
- The last owner cannot leave the project. When the owner deletes the project, members and boards go with it.
- Without a user id, the app role sees nothing.

### Server (`apps/server/src/`)
- **`db/`:** two pools (`DATABASE_URL` for the app role, `DATABASE_ADMIN_URL` for the admin role), Kysely with the types from `@covibes/db`, `withUser(userId, fn)`.
- **`auth/`:** Better Auth configuration, middleware that attaches the user to every request, and the handler under `/api/auth/*`.
- **`integrations/mail/`:** interface `sendMail`, locally the development mailbox (the latest 50 mails).
- **API**, each with Zod and the error format `{ error: { code, message } }`:
  - `GET /api/config`: public settings, e.g. whether the GitLab login is configured
  - `GET /api/projects`: own projects with role and last change
  - `POST /api/projects`: `{ name }`, responds with the new project
  - `GET /api/projects/:projectId`: project, members with name and role, own role; `404` without access or for an unknown id
  - `GET /api/dev/mails`: development mode only
  - Without a session, the project routes answer `401`.
- **Environment variables (Zod):** `APP_URL` (default `http://localhost:5173`), `DATABASE_URL`, `DATABASE_ADMIN_URL`, `BETTER_AUTH_SECRET` (at least 32 characters), optionally `GITLAB_CLIENT_ID`, `GITLAB_CLIENT_SECRET`, `GITLAB_ISSUER`

### Web (`apps/web/src/`)
- **`lib/auth-client.ts`:** Better Auth client with the magic link plugin. **`lib/api.ts`:** `fetch` for `/api` with error handling.
- **Vite** forwards `/api` to the server, so session cookies stay first-party.
- **Login page `/login`:**
  - button "Sign in with GitLab". As long as GitLab is not configured, it is disabled and shows a hint.
  - email field for the login link, with a success message. In development mode there is a link to the mailbox.
  - understandable error messages, e.g. for an expired link or too many attempts
- **Route guard:** without a session, `/` and `/p/*` lead to `/login`, and after signing in the user returns. Redirects only go to paths within the app.
- **Project list `/`:**
  - own projects with name, role and "last changed"
  - button "Create project": dialog with a name field, then straight into the new project
  - a friendly empty state without projects
- **Workspace `/p/$projectId`:**
  - loads the project
  - shows the project name in the header
  - the avatar group shows the real members; oneself is "You"
  - no access or an unknown id leads to "Project not found" with a link to the list
- **Account menu** on one's own avatar with "Sign out" (Radix dropdown menu)
- **Development mailbox `/dev/mails`:** development mode only

## Out of scope
- invitations, changing roles, read-only link (spec 21)
- two-factor setup in the UI, sign-in with GitHub or Google
- real email delivery and security headers (deployment)
- final design of login and project list (spec 33)

## Dependencies
- Specs 02a and 03
- `better-auth`, `@tanstack/react-query` (current versions, respecting pnpm's minimum release age)
