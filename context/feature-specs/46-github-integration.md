# 46 GitHub App integration and GitLab compatibility

## Goal

GitHub is the primary repository provider alongside the existing GitLab provider.
Teams connect a repository through a GitHub App installation, read its source and
issues, hand approved plans over as issues and pull requests, review pull requests
against the project architecture, and merge only the precise revision explicitly
approved by an authorized person. Existing GitLab connections remain usable.

Owner authorization: 2026-11-17, all remaining feature specs. This integration is
separate from signing in to Covibes with GitHub (spec 42). New product styling is
owned by spec 55; this unit supplies the functional provider contracts and API.

## Decisions and boundaries

- The operator registers a GitHub App and supplies its ID, slug, OAuth client ID,
  client secret, RSA private key and webhook secret as `GITHUB_APP_*` environment
  variables. No coding-agent, plugin or GitHub CLI credentials enter the app.
- The App requests repository metadata read, contents write, issues write and
  pull requests write. Installation tokens are narrowed to one repository and
  those capabilities. Workflow files are not included in generated plan packages.
- A Covibes project has one connected repository. The connection records its
  provider, immutable repository ID, full name and installation. Only a project
  owner can select or remove it. Replacing or removing it invalidates pending
  proposals through the existing repository-change rules.
- Connecting a GitHub integration account uses the App's user authorization
  flow with the signed-in Covibes session and a short-lived, purpose-separated
  state. It is not a Covibes login. Selection is verified through the user's
  installation/repository access and write permission, not a supplied repository
  URL or an unverified installation callback parameter.
- User integration tokens are encrypted with the existing AES-256-GCM token
  store key. Installation tokens are short-lived and are not sent to browsers,
  model context, logs or public database roles. Private App keys stay in operator
  configuration. An absent App configuration makes GitHub unavailable.
- API requests go only to the fixed GitHub REST and OAuth origins. Reject unsafe
  owner/repository names, nonpositive IDs, path traversal, unexpected redirects,
  excessive response bodies and malformed upstream data. Never follow upstream
  pagination or download URLs with a token to an arbitrary host.
- The existing approval queue and member rights remain authoritative. The App is
  the technical writer, while the approving Covibes person is recorded in the
  action log and generated text. An installation does not grant project access.
- Repository requests retain provider and repository identity. The worker checks
  the target and current approver authorization again before obtaining scoped
  installation access. A removed installation or revoked access fails closed.
- GitHub pull requests map to the provider-neutral review/request model. Internal
  historical `mergeRequest` names remain compatible; public metadata identifies
  the provider. The integration does not translate GitHub HTTP into fake GitLab
  endpoints.

## Provider contracts

The provider service chooses readers, blob comparison, issue-state readers,
pull/merge-request metadata and writers. The existing GitLab modules implement
the same boundaries. Bounds remain: 200 directory entries, 1 MiB text files,
30 listed issues/requests, 20 comments and 30 changed files per review. Omitted or
truncated upstream data is reported, not represented as a complete result.

GitHub operations use the official REST API:

- App JWT (RS256, at most ten minutes), installation lookup and a repository-scoped
  installation access token; App OAuth user authorization for installation access.
- Repository metadata, contents/tree/blob and bounded issue/comment reads.
- Milestones and issues derived from plan tasks with durable per-action markers.
- Git database blobs, trees, commits and non-forced refs to publish all package
  files atomically on a dedicated branch; preserve create-only files and delete
  nothing. An existing equal tree is a successful retry.
- Pull request lookup by source branch before creation; merge with the approved
  head SHA; an already merged matching pull request is a successful retry.
- Pull request comments carry an action marker and are looked up before retrying
  an operation whose previous response was lost. Reviews generated by the model
  remain local until separately approved for posting.

The transport does not blindly retry writes. Durable action state and semantic
lookups handle ambiguous outcomes. Rate limits, upstream failures and conflicts
are explicit failures. No force pushes or bypasses of repository protection.

## Webhooks and synchronization

- One App webhook endpoint verifies `X-Hub-Signature-256` over the bounded raw
  request bytes using a timing-safe comparison before parsing the event.
- Validate delivery ID, event, installation and immutable repository ID. Deduplicate
  deliveries transactionally. Only matching connected projects are queued.
- Issue and pull request events accelerate the existing throttled state sync;
  webhook content is not trusted as the final task state or as an instruction.
- Installation deletion/suspension and repository removal invalidate affected
  connections. Unknown or unauthorized events do not expose project existence.
- Periodic/open-project/manual reads remain the correctness path; webhook
  delivery is not assumed to be reliable.

## Persistence and API

Migration `0048_github_integration.sql` adds private encrypted GitHub integration
accounts, project installation bindings, delivery deduplication and the provider
discriminator. New tables have RLS and explicit grants in the same migration.
Existing GitLab account cascades and member-removal behavior remain intact.

API provides GitHub availability, integration connect/callback/disconnect,
installation repository selection and project connection. Existing project Git
request, review, package comparison and sync endpoints work for either provider.
Missing provider fields in legacy calls retain their GitLab interpretation.
Frontend layout and the final platform selector are integrated by spec 55.

## Verification

Meaningful tests cover JWT claims/signatures and expiry; purpose-bound OAuth
state; encrypted token storage; repository/installation and role checks; denied
and expired credentials; fixed-origin requests, redirects and bounds; issue/PR
mapping; deterministic package commits and safe retries; approved SHA merging;
webhook HMAC and replay behavior; private-table access and GitLab compatibility.
Use injected HTTP fixtures or a development stand-in; external credentials are
not a requirement of ordinary CI.

Required checks: lint, types, formatting, targeted contract/API/database tests,
database type verification, full tests and production build. A real GitHub App
installation and multi-user review/merge exercise is an external acceptance gate
until operator configuration is supplied; fixture success is not that validation.
